# 受信側回線の調べ方(回線種別チェックリスト)

ネット品質測定は「送信側(測定を仕掛ける側)→ 受信側」の向きで接続を張るため、
**着信できる必要があるのは受信側だけ**です(送信側は Starlink の CGNAT 配下でも可)。
受信側に使う回線がどの方式かを、以下の手順で特定してください。

## 結論の早見表

| 回線の種別 | 受信側として使えるか |
|---|---|
| 固定グローバル IP(NURO Biz 等の法人オプション) | ◎ 最も無難。IP を一度登録すれば運用が安定 |
| 動的グローバル IP(PPPoE 系、NURO 個人版等) | ○ ポート開放 + DDNS(ホスト名登録)で可 |
| MAP-E 系(v6プラス / OCN バーチャルコネクト等) | △ 割当ポート範囲内に本ソフトのポート番号を変更すれば可 |
| DS-Lite 系(transix / クロスパス等) | × IPv4 ポート開放が原理的に不可 → 役割反転・VPN・VPS で回避 |
| CGNAT(モバイル回線、Starlink 標準等) | × 着信不可 → 同上 |
| **固定 IP ↔ 固定 IP** | ◎ 最も確実。DDNS 不要、どちらを送信/受信にしても可 |
| **VPN(WireGuard/Tailscale/IPsec 等)** | ◎ VPN 内部 IP で相互到達。ポート開放/DDNS 不要（下位が CGNAT でも可） |

### VPN 経由で使う場合

本ツールは通常の TCP/UDP ソケットで「相手 IP:ポート」に繋ぐだけなので、VPN 内部
アドレス(例 `10.8.0.2`、Tailscale の `100.x.x.x`)を測定先に指定すれば動く。
VPN が相互到達性を担保するため **ポート開放も DDNS も不要**(両側 CGNAT の回避策)。
- 受信側 `allowed_sources` は VPN サブネット(例 `10.8.0.0/24` / `100.64.0.0/10`)を許可
- マルチ NIC 時は `bind_ip` に **VPN インターフェースの IP** を指定するとその経路で測定
- UDP ペイロードは 1200B 設計で一般的な VPN の MTU 内。フラグメント化しない
- **注意(測定値の意味)**: VPN 越しは「衛星 + VPN トンネル」を測る。暗号化
  オーバーヘッドでスループット上限が下がり、リレー経由だと遅延も増える。
  衛星の素の実力を測るなら VPN なしの直結、VPN 業務の体感を測るなら VPN 経由、
  と使い分ける(`ネットワーク情報` のメモ欄に経路を記録すると後解析で混同しない)。

> 社内ネットワークに置く場合は、回線種別の前に **社内 FW で TCP 5301 / UDP 5302
> の着信を許可できるか**をネットワーク管理部門に確認してください。承認が難しい
> 場合は「測定専用の独立回線(固定 IP)を引いて社内 LAN と分離」が通しやすい構成です。

## STEP 1: WAN 側 IP と外から見える IP を比べる

1. ダッシュボードの「ネットワーク情報」→ **グローバル IP 取得**(または ifconfig.me)
   で「外から見える IP」をメモ。
2. ルータ管理画面で WAN 側(インターネット側)IP を確認。
3. 判定:

| ルータの WAN 側 IP | 判定 |
|---|---|
| 外から見える IP と一致 | グローバル IP 直付け → ポート開放可能 |
| `192.168.x.x` / `10.x.x.x` / `172.16〜31.x.x` | 二重 NAT。上流にもう 1 段機器がある → 上流でも同じ確認をする |
| `100.64.x.x`〜`100.127.x.x` | **CGNAT**(キャリア NAT 専用帯域)→ 着信不可 |

## STEP 2: 固定か動的か

- ISP のマイページ / 契約書で確認(確実)。
- 簡易確認: ルータを再起動して「外から見える IP」が変わるか。変わるなら動的
  → DDNS(No-IP 等)にホスト名を登録し、本ソフトの測定先には **DDNS ホスト名**で
  登録する(接続のたびに名前解決するので IP 変化に自動追従)。

## STEP 3: IPv4 over IPv6 方式(日本特有の注意)の識別

ルータの WAN 設定画面を確認:

- 「**PPPoE**」→ 従来型。グローバル IP 直付けが基本で、ポート開放は自由。
- 「**IPoE**」「v6プラス」「transix」「クロスパス」「OCN バーチャルコネクト」等
  → IPv4 アドレスを複数ユーザで共有する方式:
  - **MAP-E 系**(v6プラス等): 使えるポート番号が限定される。ルータに
    「利用可能ポート範囲」の表示があれば、その範囲内の番号に本ソフトの
    `control_port` / `udp_port` を変更すれば開放できる(ポートは config で自由に変更可)。
  - **DS-Lite 系**(transix 等): IPv4 のポート開放が**原理的に不可**。

## STEP 4: 実地確認(最終確認)

1. 受信側 PC でソフトを起動(受信サーバ ON)し、ルータでポート転送を設定。
2. **別回線**(スマホテザリング等)の PC から:
   ```bash
   python -m bdp_analyzer sender <外から見えるIP or DDNS名>
   ```
3. スループット等の数値が返れば開通。タイムアウトなら STEP 1〜3 のどこかに問題。

## 両側とも着信できない場合(SRT 的なランデブーは使えるか)

SRT のランデブーモード相当(双方が同時に相手の公開 IP:ポートへ UDP を送り合う
ホールパンチング)は技術的には可能で、**家庭用ルータの NAT 同士なら成功率が高い**
(多くが cone 型でマッピングが安定しているため)。ただし:

- 相手の公開 IP:ポートを知る手段(DDNS + 約束ポート、または STUN)が必要
- **CGNAT は symmetric 型が多く、ホールパンチは原理的にほぼ失敗**する
  (Starlink 標準プランの CGNAT も直結できずリレーに落ちる事例が多い)
- リレー経由で成立させても「リレーまでの経路」を測ることになり、
  **衛星回線そのものの品質測定にならない**

→ 両側 CGNAT があり得る運用では、下記の **VPS 受信アンカー**が最も確実
(全回線が同じアンカーへ測るため回線間の公平比較もしやすい)。

## 着信できない回線しかない場合の回避策

- **役割反転**: 固定 IP を持てる側(例: OneWeb Intellian 配下)に受信サーバを置き、
  着信できない側を送信側にする。測定は送信側から上り下り両方を取るため、
  どちらが仕掛けても得られるデータは同じ。
- **VPN オーバーレイ**(Tailscale / WireGuard): 両 PC に導入すれば NAT/CGNAT を
  越えて双方向に到達可能。測定先には VPN 内アドレスを登録。
  ※VPN のオーバーヘッド(数%)が測定値に乗る点は留意。
- **VPS**: 固定 IP の格安 VPS に受信サーバを常駐させ、全回線からそこへ測る。
  回線間の公平比較がしやすい構成でもある。
